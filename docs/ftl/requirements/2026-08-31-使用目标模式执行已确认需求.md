## 背景与目标

FTLSoul 当前把 `B：确认定稿并执行` 解释为确认需求文档后选择实际执行器，但没有要求后续
实施进入 Codex `/goal` 目标模式。一次真实实践把目标正文直接设成了 `B`，并在等待人工 QQ
验收时过早发出测试指令、继续修改和重启待测服务，还因目标模式的停滞审计产生了重复检查
与重复结果消息。

本次变更要求：用户选择 B 后，以自包含的持久目标执行已经确认的需求文档；人工验收成为
明确的等待关口，等待期间只允许受限的最小检查；用户用普通自然语言返回验收结果后，会话
承接原目标继续执行。

## 已确认的行为

### 1. B 选择启动自包含目标

- `A：确认定稿` 的含义不变：只确认并提交需求文档，不实施，也不创建目标。
- 用户明确选择 B 后，仍须先把当前需求文档改为`已确认`并完成需求确认提交，再选择项目
  实际适用的执行器。
- 随后的实施必须进入 `/goal` 目标模式。目标正文不能是单独的 `B`、文档标题或其他依赖
  隐含对话才能理解的缩写；它至少应写明：
  - 要执行的已确认需求文档精确路径；
  - 用户已经授权执行；
  - 必须按当前项目规则选择项目专用工作流或全局回退执行器；
  - 以文档完整范围、验收预期、生命周期更新和无剩余必需工作作为停止条件；
  - 不扩大文档授权、外部副作用或 Git 权限。
- `/goal` 只承载持久执行，不替代项目工作流判断、需求文档、执行器职责、本地检查点或
  验收证据。项目明确声明的适用执行工作流仍然优先；目标 Harness 自身是修改对象时仍由
  `ftl-requirements-execution` 在其外部实施。
- 目标能力不可用、创建失败或已有目标冲突时，不得静默退回普通多轮实施。保持需求文档
  `已确认`，说明实际阻塞和继续所需条件。

### 2. 发起人工验收前冻结待测状态

- 要求用户进行人工验收前，先完成所有能够独立完成且会影响待测结果的实现、自动测试、
  审计和服务准备，并记录足以识别待测状态的证据。
- 发出人工操作说明后，不得继续修改待测代码或配置，也不得重启、替换待测服务。若发现
  必须修复且会使原验收失效的问题，明确撤销原操作说明，完成修复和重新验证后再发送一份
  新说明。
- 同一人工验收关口只发送一次清晰的操作说明，说明用户应做什么、返回哪些结果，以及哪些
  结果会允许目标继续。

### 3. 等待期间只做最小权威检查

- 目标模式因同一人工阻塞自动续跑时，每个续跑回合至多执行一次直接判断该阻塞是否解除的
  最小权威检查，例如查询一次真实入站事件计数或现有进程句柄。
- 等待回合不得修改文件或外部状态，不得重启服务，不得重新运行完整测试、需求审计或其他
  与“用户是否已经完成操作”无直接关系的命令。
- 检查没有发现变化时，不重复发送完整操作说明，不虚构进展，也不把等待描述成开发进展；
  只保留必要的简短等待状态。
- 达到 Codex 目标模式对同一阻塞的停滞判定条件后，立即把目标标记为停滞，不继续制造
  新的轮询回合。

### 4. 普通自然语言结果承接原目标

- 用户在目标因人工验收而停滞后，用普通自然语言返回所需结果时，该消息视为原目标等待的
  输入证据，而不是独立答疑或新的实施请求。
- 当前回合必须从原人工关口继续：吸收结果、核对相称证据，并尽可能执行原目标的剩余步骤；
  不得只回复“收到”后结束，也不得要求用户先恢复目标才处理已经提交的结果。
- 若当前普通回合已经足以满足整份需求的完成条件，完成生命周期更新并关闭原目标。
- 若仍有必须跨后续目标回合完成的工作，而目标调度器仍处于停滞状态，说明已经吸收的结果、
  剩余工作和恢复原因，再明确引导用户点击开始或执行 `/goal resume`；不得要求用户重复提交
  已经提供的验收结果。

## 保持不变的边界

- 需求文档仍只有在用户明确选择 A 或 B 后才能从`编辑中`变为`已确认`。
- 文档确认状态本身不授权执行；只有 B 或后续明确执行授权才能启动实施。
- 项目专用工作流优先、Harness 自修改例外、全局回退执行条件和本地提交纪律保持不变。
- 目标模式不扩展 push、合并、PR、部署、发布、历史改写、删除或外部消息权限。
- 只有整份需求全部实施并通过相称验证，才能把文档标记为`执行完毕`并把目标标记为完成。

## 验收预期

- `ftl-requirements` 明确区分 A 与 B；B 创建的目标正文是文档驱动的自包含执行目标，不是
  单独的 `B`。
- 目标创建失败时不会静默改用普通实施，也不会错误改变已确认需求的生命周期状态。
- `ftl-requirements-execution` 在人工验收前冻结待测状态；等待自动续跑仅允许每回合一次最小
  权威检查，不会继续开发、重启或重复完整审计。
- 用户以普通自然语言提交人工结果后，当前回合承接原目标继续工作；确需更多目标回合时才
  引导用户恢复目标，并保留已经提交的结果。
- A/B 确认、项目工作流优先、Harness 自修改例外、执行授权、本地提交和完成判定的现有
  规则均保持有效。
- 两个修改后的 Skill 通过 `skill-creator/scripts/quick_validate.py`；仓库内全部 Skill 的
  同项校验通过，`git diff --check` 通过；README 流程图和正文与 Skill 行为一致。
