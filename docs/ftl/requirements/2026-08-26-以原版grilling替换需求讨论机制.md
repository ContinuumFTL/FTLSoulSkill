# 以原版 grilling 替换需求讨论机制

状态：已确认

## 目标

使用 mattpocock/skills 中保持原样的 `grilling` 访谈机制承担复杂需求的结构化讨论，不修改上游 `grilling`、`grill-me` 或 `grill-with-docs` 的内容；FTLSoul 继续负责项目请求路由、需求文档物化、确认生命周期、实施授权和执行器选择。

普通项目讨论必须保持轻量、只读，不因涉及计划、设计或项目决策而自动进入 `grilling`、生成需求文档或推动开发。

## 已达成的路由规则

项目请求只保留以下三条顶层路线：

1. **理解、比较或自由探讨**：进行普通只读讨论和必要的只读项目检查；不调用 `grilling`，不创建或修改需求文档，也不推导实施意图。
2. **形成需求并准备后续工作**：进入 `ftl-requirements`。只有在这条路线中，才按需使用原版 `grilling` 澄清目标、范围、业务规则和关键取舍，并将已达成共识持续物化到当前`编辑中`需求文档。
3. **明确要求实施**：继续由 `ftl-router` 按现有规则选择明确小改动、项目声明的适用工作流，或已确认需求的回退执行流程；不能仅凭实施意图绕过复杂需求的确认边界。

不设置“想把一个计划问透、压力测试”这一独立顶层路线。`grilling` 不是路由目的地，只是 `ftl-requirements` 内部可使用的讨论机制。

普通只读讨论只有在用户明确要求形成需求、定稿、记录为后续开发依据或实施时，才升级到后续路线。讨论内容变得具体、出现方案取舍或自然形成局部共识，本身都不构成升级授权。

## 职责边界

- 上游原版 `grilling` 负责决策树、frontier 分轮提问、推荐答案、事实调查与共同理解确认；FTLSoul 不改写其访谈算法。
- `ftl-requirements` 负责选择和维护权威需求文档、逐项结算共识、判断需求是否自包含，以及提供 A／B 确认选项。
- `grilling` 达成共同理解不等于需求文档已经确认，也不授权实施。
- `grill-me` 和 `grill-with-docs` 不成为 FTLSoul 的新顶层路由；是否保留为用户显式调用的上游入口，不影响本需求定义的三条顶层路线。
- 不使用 `CONTEXT.md`、ADR、上游 session 文件或聊天摘要替代 FTL 需求文档的事实归属和生命周期。

## 原版依赖的接入方式

选择**仓库内只读快照**，决定时间为 2026-08-26T18:06:37+08:00。

- 将 mattpocock 原版 `grilling` 的完整内容不加改写地保存为 `ftl-requirements` 的内部参考资源。
- 快照记录上游仓库地址、原始文件地址和固定 Git commit；实际内容必须能与该 commit 中的原文件逐字节核对。
- 内部参考资源不注册为独立 Skill，不增加“计划压力测试”顶层路由，也不允许在普通只读讨论中自动触发。
- `ftl-requirements` 进入需求澄清路线后按需读取该快照，并继续由自身维护需求文档和生命周期。
- 快照不自动跟随上游变化；以后更新必须作为单独、明确的变更进行来源核对，不能在其他任务中顺手改写。

## 验收预期

- `ftl-router` 能明确区分普通只读讨论、形成需求和明确实施三条顶层路线。
- 计划压力测试不再是独立路由，普通项目讨论不会调用 `grilling` 或落需求文档。
- `ftl-requirements` 在需要澄清时使用保持原样的上游 `grilling` 机制，同时继续逐项维护权威`编辑中`需求文档。
- 访谈完成、需求确认和实施授权仍是三个不同事件，不能互相推定。
- 原版 `grilling` 的来源和接入方式可核对；仓库验证不依赖对话记忆或不可证明的本机状态。
