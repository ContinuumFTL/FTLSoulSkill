## 目标

为 FTLSoulSkill 增加一个可跨项目自动发现的 GitHub 安全推送 Skill。当用户在任意 Git 项目中明确要求推送、发布或更新到 GitHub 时，Codex 自动使用该 Skill，先确认实际仓库状态、待推送范围、远端目标和隐私风险，再执行与用户授权完全一致的普通推送，并在推送后验证远端结果。

## 用户已经明确的需求

- Skill 面向其他项目复用，不绑定 FTLSoulSkill 当前仓库路径、远端地址、分支名或可见性。
- 当用户表达“想推送到 GitHub”等明确推送意图时允许自动发现并调用，不要求用户记住 Skill 名称。
- 正式推送前必须进行隐私检查并说明值得注意的问题，不能只执行一条 `git push`。
- 检查没有阻塞项且授权、目标均明确后，Skill 应实际完成 GitHub 推送，而不是只给出操作教程。

## 职责与流程

### 触发边界

- 只有用户当前请求明确包含推送、发布或更新 GitHub 的意图时才进入外部写入流程；完成本地修改、测试或提交本身不自动授权推送。
- Skill 自动发现保持开启。用户可以通过自然语言触发，也可以显式调用 `$ftl-github-push`。
- 先读取目标项目自己的 `AGENTS.md` 和适用工作流；项目规则决定如何形成提交，GitHub 推送 Skill 只负责发布前审查、授权核对、推送与远端验证。

### 仓库与远端核对

- 确认当前目录属于 Git 工作树，记录仓库根目录、当前分支、HEAD、工作区状态、远端列表、当前分支 upstream 和实际 GitHub URL。
- 拒绝在 detached HEAD、目标远端不明确、存在多个同等候选远端、目标不是 GitHub、认证身份或仓库归属无法可靠确认时猜测推送目标。
- 普通更新先取得远端最新引用，区分本地领先、远端领先和双方分叉；只允许普通快进推送。远端有未知更新或双方分叉时停止，不自动 pull、merge、rebase 或强推。
- 首次发布可以作为独立模式支持，但必须由用户明确给出或确认精确 GitHub 仓库、目标分支和可见性；不得擅自创建仓库、改变可见性或设置远端。

### 待推送范围与隐私检查

- 普通更新以“远端目标分支到本地待推送 HEAD”的提交和文件差异为检查范围；首次发布检查即将公开的完整分支历史和当前树，并明确说明历史泄露不能靠后续删除提交消除。
- 展示远端 URL、源分支、目标分支、待推送提交数量与摘要、文件清单、提交作者邮箱以及工作区是否仍有未提交或未跟踪内容。
- 检查常见令牌、API Key、密码、私钥、凭据文件、`.env`、云服务配置、认证缓存、个人邮箱、本机用户名、绝对路径、内部地址、私有文档以及异常的大文件或二进制文件。
- 高可信凭据、私钥或认证材料属于阻塞项，停止推送并只报告文件位置和风险类型，不在聊天或日志中回显秘密值。
- 本机路径、个人邮箱、用户名、内部说明等上下文型隐私属于警告项；必须把精确文件和影响告诉用户，由用户明确接受后才能继续公开推送。
- 隐私扫描只降低误传风险，不声称能够证明仓库绝对不含秘密；检查工具缺失或扫描范围不可靠时如实说明并停止高风险公开发布。

### 推送与验证

- 在目标、分支、待推送提交和隐私结论均确定后先执行无副作用的推送预演，再进行一次普通的精确 refspec 推送；不使用 `--force`、`--force-with-lease`、`--mirror`、`--all` 或隐式标签推送。
- 推送后读取 GitHub 远端分支提交号并与本地目标提交核对，同时报告工作区与 upstream 状态；只有远端命中预期提交才宣告完成。
- 网络、认证、权限、分支保护或服务器拒绝导致失败时停止并保留真实状态；不得通过扩大权限、改写历史、关闭保护或更换远端来绕过。

## 已确认选择

1. **未提交修改怎么处理。** 默认不自动把工作区打包提交：如果用户只说“推送”，仅推送已经存在的提交，并明确提醒未提交内容不会上云；如果用户明确要求“把当前修改提交并推送”，先交给目标项目工作流形成和验证提交，再回到本 Skill 做发布审查。
2. **是否重复确认。** 用户已经明确说“推送到 GitHub”，且现有远端、目标分支、范围都唯一、隐私扫描无警告时，把该请求视为本次普通推送授权，不再重复问一次；首次发布、目标不唯一或出现任何隐私警告时必须停下来取得明确确认。
3. **隐私检查发现普通本机路径时。** 把路径视为警告而不是一律阻塞；展示文件位置和可能暴露的信息，用户明确接受后仍可推送。令牌、密码、私钥和认证文件始终阻塞，不能用一句“无所谓”整体放行。

## 授权边界

- Skill 只能使用用户当前请求明确给出的 GitHub 推送授权，不能把过去一次推送、项目修改授权、本地提交授权或需求确认推导为新的外部写入授权。
- 不自动创建、删除、重命名或转移 GitHub 仓库，不改变公开/私有可见性、默认分支、分支保护、协作者、Actions、Secrets、Pages、Issues、PR、Release 或账号设置。
- 不改写提交历史，不自动提交未提交改动，不自动合并、变基、丢弃、暂存或清理用户文件，不删除远端分支或标签。
- 需要创建本地提交时由目标项目适用工作流决定内容、验证和提交边界；本 Skill 不绕过项目治理。
- 创建本 Skill、同步当前用户的全局 Skill 链接和推送 FTLSoulSkill 自身仓库是三种不同外部或本地动作，分别遵守当前任务的明确授权。

## 验证与验收

- 新 Skill 名称和描述能够在用户明确要求 GitHub 推送时自动命中，不吸引普通 Git 状态查询、本地提交、GitLab 推送或泛化隐私讨论。
- 使用隔离的临时 Git 仓库验证：无远端、目标不明确、无待推送提交、存在未提交文件、远端领先、双方分叉、检测到高可信秘密、出现普通路径警告、预演成功和推送后 SHA 核对等关键分支。
- 测试不得向真实 GitHub 仓库写入；推送成功路径使用本地 bare remote 或等价的隔离远端验证。
- 新 Skill 通过 `skill-creator` 的结构校验、FTLSoul 全仓库 Markdown 校验、链接预演和 `git diff --check`。
- 本地实现提交只包含本需求文档、新 Skill 和必要的调用关系或测试资源；同步本机全局 Skill 后可以从其他项目发现它。

## 停止条件

出现以下任一情况时停止：用户没有明确推送意图；目标仓库或分支不唯一；远端发生未知变化；需要非快进、历史改写或权限扩大；隐私扫描发现高可信秘密；普通隐私警告尚未获得用户接受；项目工作流要求的提交或验证没有完成；推送预演失败；实际远端 SHA 与预期不一致。
