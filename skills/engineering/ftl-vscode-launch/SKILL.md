# VS Code 一键启动

把项目真实、有效的开发启动方式写入 `.vscode/launch.json`，让用户可以从 VS Code 的“运行和调试”面板直接启动或调试，而不必每次重新输入命令。

## 面向用户的表达

在产生本次任务的面向用户聊天文本前，完整读取并使用 `ftl-soul`；其适用范围和正式产物例外以该 Skill 为准。

## 授权边界

- 配置一键启动只授权创建或维护相关 VS Code 配置，不自动授权启动服务、安装扩展、修改业务代码或提交远端。
- 用户同时明确要求启动时，才在配置和安全检查通过后启动；可能连接账号、发送消息、修改外部数据或占用长期端口的服务，不能只为验证配置而运行。
- 只修改本次启动目标涉及的配置。保留已有的其他 `configurations`、`compounds`、任务和用户改动，不把整个文件替换成单一模板。
- 不把 Token、密码、`.env` 内容或其他秘密写入 `launch.json`。

## 确认启动事实

- 先读取适用的项目规则，以及 README、项目清单、启动脚本、现有 `.vscode` 配置、环境变量示例和实际入口文件。
- 用户提供参考 `launch.json` 时，读取其启动结构和约定，但必须把工作目录、入口、端口、运行时和路径适配为目标项目的真实值。
- 确认工作区根目录、单服务或多服务结构、项目自己的解释器或运行时、包管理器、环境文件、工作目录和准确启动命令。
- 优先采用项目已经记录或实际使用的启动方式，不因参考项目使用某个框架、端口或包管理器就照搬。
- 存在多个同样合理且结果不同的启动目标，无法从项目状态确定用户所指对象时，停止并询问；不要猜一个看似常见的入口。

## 生成配置

- 没有 `.vscode/launch.json` 时创建它；已有文件时做最小合并。使用 `${workspaceFolder}` 表达项目内路径，避免写死用户机器的绝对路径。
- Python 项目优先使用 `type: "debugpy"`、`request: "launch"` 和项目实际支持的 `module` 或 `program`。设置正确的 `cwd` 和集成终端；项目存在自有虚拟环境时显式绑定它，只有源码布局确实需要时才设置 `PYTHONPATH`，只有环境文件存在且适用时才设置 `envFile`。
- Node 项目遵循仓库现用的 npm、pnpm、yarn 或其他运行方式，不擅自切换包管理器；在 Windows 上按 VS Code 的实际调用要求使用相应 `.cmd` 入口。
- 多服务项目为独立进程建立独立启动项；只有用户需要共同启动时才增加 compound。compound 中的名称必须与启动项完全一致，需要整体停止时设置 `stopAll: true`。
- 启动项名称应简短、可辨认，并说明启动的服务或用途。

## 验证与交付

- 验证 JSON 或 JSONC 结构，以及配置引用的解释器、程序、模块、工作目录、脚本和环境文件；可选资源必须明确是有意可选，不能把缺失路径当成通过。
- 执行不产生外部副作用的解析检查，例如 Python 模块导入、配置加载或包管理脚本存在性检查。不得把没有实际执行的检查写成已通过。
- 用户明确要求同时启动且当前环境能控制 VS Code 时，使用新配置启动；无法直接控制 VS Code 时，可以运行等价的已确认命令，但必须说明这是等价启动，不能声称已经测试 F5。
- 交付时说明新增或更新的启动项名称、F5 使用方法、实际验证结果，以及仍需用户安装的调试扩展或满足的外部条件。

## 本地提交

配置完成且相称验证通过后，把本次相关 VS Code 配置定义为独立提交单元，使用 `ftl-local-commit` 创建本地 Git commit。只允许暂存本次明确修改的路径；不是 Git 仓库、存在混杂改动或无法安全提交时保留工作并如实说明。
