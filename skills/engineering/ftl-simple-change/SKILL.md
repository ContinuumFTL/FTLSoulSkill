# 明确改动

直接完成用户已经决定且符合全部准入条件的修改。不要要求用户再确认同一授权，也不要为简单改动建立形式化需求、Plan、Implementation 或 Eval 文档；简单修改不新增项目角色，也不要求独立 Evaluator。

## 面向用户的表达

在产生本次任务的面向用户聊天文本前，完整读取并使用 `ftl-soul`；其适用范围和正式产物例外以该 Skill 为准。

## 准入条件

开始前必须同时确认：

- 用户已经明确决定目标、预期结果和作用范围。
- 改动局部、低风险、可撤销，并存在直接且相称的验证方法。
- 不需要改变 Goal、Milestone、Spec、Plan、Eval、Agent 角色契约、授权边界、生命周期状态或其他权威 harness 语义。
- 工作不属于当前有效 Plan 的执行范围；已在 Plan 内的工作即使代码差异很小，也继续由该 Plan 的 Generator、Evaluator 和状态规则管理。

对 harness 文件只允许错字、格式、失效链接等能够证明不改变权威语义的机械修正。按文件数量、代码行数或预计耗时不能单独判断为简单修改。

任一条件不成立时不要使用本 Skill；转到 `ftl-requirements` 或适用的项目 Planner harness。

## 实施

- 先读取适用的项目规则并检查相关现状，只修改请求明确涉及的范围。
- 缺少次要信息时采用保守、易撤回的假设并在交付时说明；缺少会改变目标、业务规则、权限或核心结果的决定时停止等待。
- 若检查发现的问题能在原授权范围内安全修复，可以继续完善；出现需求歧义、范围扩大、关键假设失效、风险升级或必须修改权威 harness 语义时，停止超出原授权的动作，并转到需求流程或项目 Planner。
- 保留用户和其他任务的既有改动，不覆盖、不回滚、不混入本任务。

## 验证

执行与风险相称的实际检查，例如目标测试、类型检查、构建或行为检查。优先使用项目已有命令；不得发明命令或把未运行的检查写成已经通过。

验证失败时，在原授权范围内可以继续修复。无法修复、无法验证或需要关键决定时，保留真实证据并报告未完成状态。

交付时报告实际变更范围、验证方法和验证结果；不得用“改动很小”代替验证，也不得把自验证表述为独立 Eval。

## 本地提交

修改完成且相称检查通过后，将本次完成的改动定义为一个可独立理解、审查和回退的提交单元，使用 `ftl-local-commit` 创建本地 Git commit。

向其提供本次修改的提交目的、允许暂存的明确路径和已经执行的验证结果。无法创建提交时，保留能够安全保留的工作，并如实说明原因和当前状态。
