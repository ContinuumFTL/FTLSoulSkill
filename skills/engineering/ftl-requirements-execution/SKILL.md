# 执行已确认需求

本 Skill 是全局回退执行器。项目没有声明适用于当前需求的执行工作流时，它可以执行已确认且获授权的需求；项目 Harness 治理机制本身是直接修改对象时，它也负责在目标 Harness 之外实施。它不与已经接管任务的项目工作流重复执行。

## 面向用户的表达

在产生本次任务的面向用户聊天文本前，完整读取并使用 `ftl-soul`；其适用范围和正式产物例外以该 Skill 为准。

只在以下任一条件成立时开始：

- 用户选择了 `B：确认定稿并执行`；
- 用户此前确认文档后，又明确授权执行该文档。

需求还必须处于`已确认`，或者处于项目明确定义为可执行并规定了完成转换的等价状态。选择 A、只有生命周期状态、存在实现 commit，均不能单独推导出执行授权。已经完成的文档是历史记录，不是待执行任务。

开始前必须读取项目规则并判断是否存在适用于该需求的执行工作流：

- 需求直接创建、修改或替换项目 Harness 的角色契约、权威职责、任务路由、授权、事实归属、生命周期、协作规则或治理检查：被修改的 Harness 是目标而不是执行器；需求自包含且授权充分时继续本 Skill，不为它创建项目没有要求的治理结构。
- 项目明确声明了适用执行工作流：停止本 Skill，把已确认需求和用户执行意图交给该工作流；不得重复执行已经由它管理的内容。
- 项目没有适用执行工作流，且需求自包含、授权充分并能用本 Skill 的通用检查点纪律安全执行：继续。
- 项目没有适用工作流，但需求依赖未提供的执行机制、关键规则或权限：报告没有可用执行器并停止，不得猜测实施。

既有需求若使用项目定义的额外状态，应按该项目可靠规则判断它是否允许执行、是否已经交给其他执行器，以及完成时如何转换。任一项没有可靠定义时停止，不得为了使用本 Skill 擅自改写状态。修改具体产品事实、实现、测试或状态仍属于普通项目工作，不因目标文件由 Harness 导航而适用治理机制例外。混合请求必须拆分；治理部分完成后，产品部分交给修改后实际生效的项目工作流。

## 执行边界

以当前获授权且状态为`已确认`的文档为边界；项目额外生命周期只有在规则明确声明当前状态可执行并规定完成转换时才适用。历史文档只提供必要解释或审计证据，不自动并入当前需求。

开始前确认文档状态、内容和授权。当前文档不自包含、与可靠历史证据冲突，或必须猜测关键规则时，停止受影响的实施并请求决定。

任务被实际验证打回时，可以在原授权范围内继续完成剩余工作或修复；扩大目标、权限或副作用范围前必须重新取得授权。

## 实施与检查点

- 按可独立理解、验证、审查和回退的任务结果推进，不按对话轮次或每次编辑机械切分。
- 每个独立结果完成并通过相称验证后，将该结果定义为实现检查点，向 `ftl-local-commit` 提供提交目的、允许暂存的明确路径和验证结果，由其创建本地实现 commit。
- 相关验证失败、结果损坏或仍是临时状态时，不提交该单元。
- 已经形成的实现 commit 是检查点，不证明整份需求已经完成；后续修复应使用新提交，不默认 amend 或 squash。

`ftl-local-commit` 无法安全创建检查点时，如实说明；不得伪造提交，也不得据此把未完成内容标记为完成。

## 目标模式中的人工验收

需要用户完成外部操作或人工判断时，先完成所有能够独立完成且会影响验收结果的实现、自动
测试、审计和服务准备，并保留足以识别待测状态的证据。随后发送一次清晰的操作说明，写明
用户应执行的步骤、应返回的结果和允许目标继续的条件。

发出说明后冻结待测状态：不得继续修改待测代码或配置，不得重启或替换待测服务。若后来
发现必须修复且会使原验收失效的问题，先明确撤销原说明，完成修复与重新验证，再发送新的
验收说明。

同一人工阻塞触发目标自动续跑时，每个回合至多执行一次直接判断阻塞是否解除的最小权威
检查，例如查询一次真实入站事件计数或已经确认存活的进程句柄。等待回合不得写入文件或
外部状态，不得重启服务，不得重新运行完整测试、需求审计或无关命令。没有变化时不重复
完整操作说明，不虚构进展，只报告必要的简短等待状态。严格达到目标模式对同一阻塞的停滞
条件后，立即将目标标记为停滞。

用户以普通自然语言返回此前等待的信息或验收结果时，把该消息作为原目标的输入证据，在
当前回合从人工关口继续：吸收结果、核对相称证据，并尽可能完成剩余步骤。不得只回复
“收到”后结束，也不得要求用户先恢复目标才处理已经提交的结果。当前回合足以完成整份
需求时，完成生命周期更新并关闭原目标；仍有必须跨后续目标回合完成的工作且调度器仍停滞
时，说明已吸收的结果、剩余工作和恢复原因，再引导用户点击开始或执行 `/goal resume`，
不得要求用户重复结果。

## 整体验收

对当前需求文档的全部内容执行与风险相称的实际检查。使用项目真实支持的测试、构建、静态检查、行为检查和变更审阅，不得发明命令或报告未执行的验证。

- 全部内容已经实施且检查通过：进入完成状态更新。
- 检查未通过但能在原授权范围内修复：不进入完成状态，保留失败证据，修复后重新检查。
- 只完成部分内容：不进入完成状态，继续剩余任务。
- 无法验证、无法继续或必须等待关键决定：不进入完成状态，报告真实阻塞。

以上未完成分支默认保持`已确认`；从项目定义的等价可执行状态进入时保持当前状态，只有项目规则明确规定失败、暂停或部分完成转换时才按其转换，不得擅自映射回默认状态。

## 标记执行完毕

只有整份文档全部实施并通过实际验证，才将默认状态从`已确认`改为`执行完毕`，并写入本次事件实际发生时带时区偏移的 ISO 8601 执行完毕时间。项目定义了等价可执行状态时，使用该项目明确规定的完成转换；没有规定时不得猜测完成状态。

既有文档若包含旧版全局 Skill 或项目规则定义的额外元数据，只按其可靠来源更新；不得伪造事件、删除仍有意义的字段，或把这些字段加入其他新文档。

检查生命周期字段与验证证据，将本次完成状态及其直接相关内容定义为独立的状态提交单元，使用 `ftl-local-commit` 创建本地状态 commit。无法安全提交时如实说明，不伪造记录。

执行完毕文档此后作为历史基线；相关新需求必须新建 `编辑中` 文档，不得原地改写。
