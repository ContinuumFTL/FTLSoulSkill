# 执行已确认需求

只在以下任一条件成立时开始：

- 用户选择了 `B：确认定稿并执行`；
- 用户此前确认文档后，又明确授权执行该文档。

选择 A、文档处于 `已确认`、存在实现 commit，均不能单独推导出执行授权。`执行完毕` 文档是历史记录，不是待执行任务。

## 执行边界

以当前获授权的已确认文档为边界。历史文档只提供必要解释或审计证据，不自动并入当前需求。

开始前确认文档状态、内容和授权。当前文档不自包含、与可靠历史证据冲突，或必须猜测关键规则时，停止受影响的实施并请求决定。

任务被实际验证打回时，可以在原授权范围内继续完成剩余工作或修复；扩大目标、权限或副作用范围前必须重新取得授权。

## 实施与检查点

- 按可独立理解、验证、审查和回退的任务结果推进，不按对话轮次或每次编辑机械切分。
- 每个独立结果完成并通过相称验证后，将该结果定义为实现检查点，向 `ftl-local-commit` 提供提交目的、允许暂存的明确路径和验证结果，由其创建本地实现 commit。
- 相关验证失败、结果损坏或仍是临时状态时，不提交该单元。
- 已经形成的实现 commit 是检查点，不证明整份需求已经完成；后续修复应使用新提交，不默认 amend 或 squash。

`ftl-local-commit` 无法安全创建检查点时，如实说明；不得伪造提交，也不得据此把未完成内容标记为完成。

## 整体验收

对当前需求文档的全部内容执行与风险相称的实际检查。使用项目真实支持的测试、构建、静态检查、行为检查和变更审阅，不得发明命令或报告未执行的验证。

- 全部内容已经实施且检查通过：进入完成状态更新。
- 检查未通过但能在原授权范围内修复：保持 `已确认`，保留失败证据，修复后重新检查。
- 只完成部分内容：保持 `已确认`，继续剩余任务。
- 无法验证、无法继续或必须等待关键决定：保持 `已确认`，报告真实阻塞。

## 标记执行完毕

只有整份文档全部实施并通过实际验证，才将状态从 `已确认` 改为 `执行完毕`，并写入本次事件实际发生时带时区偏移的 ISO 8601 执行完毕时间。

检查生命周期字段与验证证据，将本次完成状态及其直接相关内容定义为独立的状态提交单元，使用 `ftl-local-commit` 创建本地状态 commit。无法安全提交时如实说明，不伪造记录。

执行完毕文档此后作为历史基线；相关新需求必须新建 `编辑中` 文档，不得原地改写。
