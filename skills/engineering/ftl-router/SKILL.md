# FTL 工作流路由器

根据用户当前请求、适用的项目规则和可靠的项目现状，选择与授权相符的工作路线。这里只负责编排；具体执行纪律由职责更窄的 Skill 承担。

## 面向用户的表达

在产生本次任务的面向用户聊天文本前，完整读取并使用 `ftl-soul`；其适用范围和正式产物例外以该 Skill 为准。

## 选择路线

先按用户当前意图区分三条顶层路线。项目话题本身、计划是否具体或对话中是否出现取舍，都不能替代用户意图。

### 1. 只读讨论

用户要回答、解释、比较、自由探讨、审查、诊断或只读计划时，进行相应分析及必要的只读检查，不修改项目文件，也不顺手实施建议。即使讨论涉及项目计划、设计选择或压力测试，只要用户没有明确要求形成后续工作依据、维护需求文档或实施，就保持本路线；局部共识不自动升级路线。

### 2. 形成需求

用户明确希望把当前内容形成、记录、修订或确认为后续工作依据，或者当前请求直接处理需求文档及其生命周期时，使用 `ftl-requirements`。需要共同决定目标、范围、业务规则或关键取舍时，由该 Skill 使用其内部结构化讨论机制；`grilling` 不作为独立顶层路线。

### 3. 明确实施

用户明确要求修改、构建或执行时，按实际范围继续选择：

- 只有同时满足以下条件的项目修改才使用 `ftl-simple-change`：目标、预期结果和作用范围均已明确；改动局部、低风险、可撤销且有直接验证方法；不改变项目的权威职责、任务路由、授权边界、生命周期或治理检查；也没有项目专用工作流正在管理该变更。
- 目标和关键取舍已经明确、但修改不符合小改动条件：项目明确声明了适用执行工作流时交给该工作流；否则使用 `ftl-requirements` 形成可确认的自包含边界，不能因为方案清楚就绕过非平凡变更的确认流程。
- 当请求的直接目标是创建、修改或替换项目 Harness 的治理机制时，被修改的项目 Harness 不是该请求的适用执行器：
  - 治理机制包括角色契约、权威职责、任务路由、授权规则、事实归属、生命周期、文档协作规则，以及执行这些语义的校验脚本；
  - 关键取舍未确定时使用 `ftl-requirements`；需求已经确认且用户明确要求执行时，使用 `ftl-requirements-execution` 在目标 Harness 之外实施；
  - 修改具体产品事实、实现、测试或状态仍属于使用项目 Harness，不因目标文件由 Harness 导航而自动适用自修改例外；
  - 同一请求混合治理修改和产品开发时按性质拆分。先完成治理修改，再把产品部分交给修改后实际生效的项目工作流。
- 用户明确要求执行一份已经确认但尚未完成的需求文档：先使用 `ftl-requirements` 核对文档状态和当前版本，再读取项目规则判断是否声明了适用于该需求的执行工作流。
  - 需求直接修改项目 Harness 治理机制：目标 Harness 因为是修改对象而不适用；使用 `ftl-requirements-execution`。
  - 项目明确声明了适用工作流：遵循该工作流，不由全局 Skill 臆测它的角色、文档或状态结构。
  - 没有适用执行工作流，但需求自包含且符合通用执行边界：使用 `ftl-requirements-execution` 回退执行。
  - 需求不自包含或依赖缺失的执行机制、关键规则或权限：说明当前没有可用执行器，保持`已确认`并停止，不得擅自实施。

已确认需求仅因存在或进入`已确认`状态，不自动触发项目工作流或执行。同一请求混合多种性质时分别路由；可以完成已明确、已授权且能独立成立的部分，未决部分继续讨论。

不能只因项目存在 `AGENTS.md`、测试或某种文档名称就认定专用 Harness 适用。应从项目规则、真实入口和当前任务范围确认该工作流是否明确承担本次执行。

小改动如果会改变权威 Harness 语义，或者已经由项目专用工作流管理，即使文件少、代码行数少，也不能走简单修改旁路。直接改变项目 Harness 治理机制时转到 `ftl-requirements`；普通项目工作交给实际适用的项目工作流。`ftl-simple-change` 执行中出现歧义、范围扩大、关键假设失效或风险升级时，同样按这个层级重新路由。

不要预先加载全部下游 Skill。完成判断后，只读取当前路线需要的 Skill。

当前路线需要创建本地提交时，由上游业务 Skill 决定提交目的、精确范围、验证条件和流程语义，再使用 `ftl-local-commit` 完成安全提交。路由器不替业务流程决定提交时机或提交单元。

## 共同边界

用户当前明确指令优先于本 Skill 的默认工作方式；更具体的项目规则可以补充约束。无法安全化解冲突时，停止冲突动作并如实说明。

缺少不会改变目标、业务规则、权限或核心结果的次要信息时，可以采用保守、可说明且易撤回的假设。缺少关键决定时不得猜测；能从项目状态查明的信息应先检查。

本地文件修改或本地 commit 不授权 push、合并、创建 PR、部署、发布、改写历史、删除范围外内容或发送外部消息。不得从一种授权推导另一种授权。

不得虚构文件、项目状态、工具能力、命令结果、时间、验证证据、Git commit 或外部状态。

## 失败与等待

必要工具或状态不可用、验证失败且无法继续、或者缺少影响核心结果的用户决定时，不得声称任务完成。说明：

1. 已完成且能独立成立的部分；
2. 实际执行的检查；
3. 阻塞原因；
4. 继续所需的决定或外部条件；
5. 文件、文档状态和本地 commit 的真实状态。
