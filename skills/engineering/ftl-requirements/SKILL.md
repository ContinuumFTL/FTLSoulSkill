# 需求澄清与文档生命周期

帮助用户逐项明确目标、范围、约束、业务规则、关键取舍和验收预期。提出有判断的建议，但不要把建议当成用户同意，也不要把文档确认当成实施授权。

## 面向用户的表达

在产生本次任务的面向用户聊天文本前，完整读取并使用 `ftl-soul`；其适用范围和正式产物例外以该 Skill 为准。

## 逐项结算讨论

用户一轮可能回应多个分项。分别处理：

- 明确接受或明确选择的分项视为已达成一致。
- 要求修改、解释或比较的分项保持未决。
- 含义不明确且会影响目标、业务规则、权限或核心结果的分项必须追问。
- 用户明确要求暂不记录的内容不写入文档。

继续讨论前，将本轮已明确达成一致的内容写入当前 `编辑中` 文档，并简要说明已记录和仍待讨论的内容。部分共识写入不代表整份文档已经确认，也不授权实施。

例如，AI 用 Markdown 编号提出：

1. Spec 和 Plan 是否严格一对一；
2. Implementation 如何同时保存现状和失败过程；
3. Spec 和 Milestone 的完成公式；
4. 用户和 Agent 分别拥有什么决定权。

用户只回复：

> 1. 按你推荐的来
> 2. 按你推荐的来
> 3. 按你推荐的来
> 4. 这个我们待会儿接着讨论

即使用户没有要求写文档，也应先按“选择文档”检查相关文档状态，维护现有文档或新建 `编辑中` 文档，将第 1–3 项对应的结论写入并告知用户“第 1–3 项已记录，第 4 项仍待讨论”，然后再继续讨论第 4 项。不要等待用户提出“写文档”，也不要把是否新建文档的流程判断推给用户。

## 选择文档

每次处理旧需求或历史实现前，重新检查相关需求文档和实际状态，不只依赖对话记忆。

- 没有对应文档：新建 `编辑中` 文档。
- 对应文档为 `编辑中`：原地维护。
- 对应文档为 `已确认`或`吸收完毕`但未执行完毕：需要修改时退回`编辑中`，将当前版本确认时间、吸收时间和吸收记录分别恢复为`未确认`、`未吸收`和`未吸收`。
- 对应文档为 `执行完毕`：保留历史基线，另建 `编辑中` 文档，注明直接关联的旧文档和本次变更主题。

只维护当前请求相关的文档，不批量改写历史。历史文档用于必要解释和审计，不自动成为当前实施依据。

## 文档位置与格式

所有由该 Skill 新建的需求文档统一使用：

`docs/ftl/requirements/YYYY-MM-DD-简短标题.md`

除非用户在当前请求中明确指定其他位置，否则项目已有的泛化文档目录、旧约定或历史位置不得覆盖该路径。维护既有需求文档时原地更新，不因本规则自动迁移或重命名；需要迁移历史文档时必须另行取得明确授权。

日期使用实际创建日期。一级标题不包含日期和扩展名。每份文档记录：

```text
状态：编辑中 | 已确认 | 吸收完毕 | 执行完毕
建立时间：YYYY-MM-DDTHH:mm:ss±HH:mm
确认时间：未确认 | YYYY-MM-DDTHH:mm:ss±HH:mm
吸收时间：未吸收 | YYYY-MM-DDTHH:mm:ss±HH:mm
吸收记录：未吸收 | 不适用（无专用 harness） | 不适用（项目 harness 为修改对象，全局执行） | 实际创建或修改的 harness 路径
执行完毕时间：未执行完毕 | YYYY-MM-DDTHH:mm:ss±HH:mm
```

时间使用对应事件实际发生时带时区偏移的 ISO 8601 值。不得用当前时间伪造历史时间；可靠记录无法证明时写 `未知` 并说明原因。

该命名规范只约束新文档，不构成批量重命名既有文档的授权。存在多份相关文档时，逐份选择、确认、提交和判断完成状态，不把一份文档的授权或生命周期扩展到其他文档。

状态含义：

1. `编辑中`：仍在讨论，不能作为实施依据。
2. `已确认`：用户确认了当前内容，可以作为开发或吸收依据，但状态本身不授权吸收或执行。
3. `吸收完毕`：适用项目 Planner 已把当前已确认版本完整映射到对应 harness，追溯有效且没有未解决冲突；这不表示实施或 Eval 已完成。
4. `执行完毕`：全部内容已经实施，并通过相称的实际验证。

`已确认`和`吸收完毕`都是用户已确认的有效版本。项目没有适用专用 harness 时，文档可以停留在`已确认`；通用回退执行完成后可从`已确认`直接进入`执行完毕`，不得为满足状态形式伪造一次吸收。

## 吸收

需求确认后不自动触发吸收。只有用户明确提出吸收或执行意图，且项目规则表明存在适用于本需求的专用 harness 时，才由该项目的 Planner 执行吸收：

- 按实际范围创建或修改对应 Milestone、Specs 和 Plans，不机械要求每份需求产生全部类型。
- 每份由需求创建或修改的 harness 文档记录源需求路径和确认时间，不复制需求正文。
- 原需求记录实际吸收时间，以及创建或修改的 Milestone、Specs 和 Plans 路径；不适用的类别明确写`不适用`。
- 只有全部内容已映射或明确无需 harness 变更、没有未解决冲突且追溯路径有效时，才将主状态改为`吸收完毕`。

当需求的直接目标是创建、修改或替换项目 harness 的治理机制时，被修改的 harness 不是适用吸收方。该需求保持`已确认`并在用户明确授权后交给全局 `ftl-requirements-execution`；不得创建治理 Milestone、Spec 或 Plan 来让 harness 吸收自己的替代规则。具体产品 Milestone、Spec、Plan、Implementation 和 Eval 的日常内容更新仍按项目 harness 吸收与执行规则处理。

Generator、Evaluator 和 Skill 本身不作为独立状态修改者。由项目 Planner 在遵循本 Skill 生命周期规则时回写需求状态。

## 保持当前需求自包含

修改执行完毕的历史基线时，新文档必须在本次范围内完整写清修改后希望生效的目标、业务规则、必要约束、需要保留的相关行为和验收预期。不得要求执行者递归拼接多份历史文档才能还原当前需求。

只记录直接相关的前序文档，以及确有助于避免误解的简短变更原因；不要复制无关模块或完整演变史。

## 确认

结合目标、范围、业务规则、关键选择、验收预期和可实施性，判断文档是否足以支持开发。

仍有关键缺口或用户提出修改时，保持 `编辑中` 并继续讨论。文档已经完善时，明确提供：

- `A：确认定稿`：确认并提交需求文档，不实施项目功能。
- `B：确认定稿并执行`：先确认并提交需求文档。需求直接修改项目 harness 治理机制时，该 harness 不视为适用执行器，交给全局 `ftl-requirements-execution`；其他需求再按项目规则优先选择适用的专用 Planner harness，没有适用 harness 且符合通用执行边界时使用回退执行。

只有用户明确选择 A 或 B，才把对应文档改为 `已确认` 并写入实际确认时间。含糊回答不能推定为确认或执行授权。

## 文档确认提交

确认后检查生命周期字段和实际内容，将本次确认的需求文档定义为独立的文档确认提交单元，使用 `ftl-local-commit` 创建本地 commit。只把该需求文档列为允许暂存的路径，不把其他文档或实现改动纳入本次提交。

无法创建提交时如实说明，不伪造提交，也不把文档确认提交失败解释为功能执行授权。

选择 A 后结束，不吸收或执行项目功能。选择 B 后把当前已确认文档和明确执行意图交回统一路由：直接修改项目 harness 治理机制时使用全局 `ftl-requirements-execution`；其他需求适用专用 Planner harness 优先，通用执行只在没有适用 harness 时回退。
