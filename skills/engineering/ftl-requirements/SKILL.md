# 需求澄清与文档生命周期

帮助用户逐项明确目标、范围、约束、业务规则、关键取舍和验收预期。提出有判断的建议，但不要把建议当成用户同意，也不要把文档确认当成实施授权。

## 面向用户的表达

在产生本次任务的面向用户聊天文本前，完整读取并使用 `ftl-soul`；其适用范围和正式产物例外以该 Skill 为准。

## 使用边界

普通回答、解释、比较和自由探讨不属于本 Skill；它们保持只读，也不因出现项目计划、设计取舍或局部共识而自动形成需求。只有用户明确希望形成后续工作依据、维护需求文档或实施非平凡变更，统一路由才进入本 Skill。

## 逐项结算讨论

用户一轮可能回应多个分项。分别处理：

- 明确接受或明确选择的分项视为已达成一致。
- 要求修改、解释或比较的分项保持未决。
- 含义不明确且会影响目标、业务规则、权限或核心结果的分项必须追问。
- 用户明确要求暂不记录的内容不写入文档。

继续讨论前，将本轮已明确达成一致的内容写入当前 `编辑中` 文档，并简要说明已记录和仍待讨论的内容。部分共识写入不代表整份文档已经确认，也不授权实施。

例如，AI 用 Markdown 编号提出：

1. 用户最终会看到什么结果；
2. 输入不可靠时是否阻断输出；
3. 哪些外部写入需要单独授权；
4. 用户和 Agent 分别拥有什么决定权。

用户只回复：

> 1. 按你推荐的来
> 2. 按你推荐的来
> 3. 按你推荐的来
> 4. 这个我们待会儿接着讨论

即使用户没有要求写文档，也应先按“选择文档”检查相关文档状态，维护现有文档或新建 `编辑中` 文档，将第 1–3 项对应的结论写入并告知用户“第 1–3 项已记录，第 4 项仍待讨论”，然后再继续讨论第 4 项。不要等待用户提出“写文档”，也不要把是否新建文档的流程判断推给用户。

## 选择文档

每次处理旧需求或历史实现前，重新检查相关需求文档和实际状态，不只依赖对话记忆。

- 没有对应文档：新建 `编辑中` 文档。
- 对应文档为 `编辑中`：原地维护。
- 对应文档为`已确认`但未执行完毕：需要修改时退回`编辑中`，将当前版本确认时间恢复为`未确认`。
- 对应文档为 `执行完毕`：保留历史基线，另建 `编辑中` 文档，注明直接关联的旧文档和本次变更主题。
- 对应文档使用项目明确定义的额外生命周期状态：遵循该项目规则；只有规则明确说明该状态允许执行及其完成转换时，才能使用全局回退执行器。全局 Skill 不猜测状态含义，也不把它改写成默认状态。

只维护当前请求相关的文档，不批量改写历史。历史文档用于必要解释和审计，不自动成为当前实施依据。

## 文档位置与格式

所有由该 Skill 新建的需求文档统一使用：

`docs/ftl/requirements/YYYY-MM-DD-简短标题.md`

除非用户在当前请求中明确指定其他位置，否则项目已有的泛化文档目录、旧约定或历史位置不得覆盖该路径。维护既有需求文档时原地更新，不因本规则自动迁移或重命名；需要迁移历史文档时必须另行取得明确授权。

日期使用实际创建日期。一级标题不包含日期和扩展名。每份文档记录：

```text
状态：编辑中 | 已确认 | 执行完毕
建立时间：YYYY-MM-DDTHH:mm:ss±HH:mm
确认时间：未确认 | YYYY-MM-DDTHH:mm:ss±HH:mm
执行完毕时间：未执行完毕 | YYYY-MM-DDTHH:mm:ss±HH:mm
```

时间使用对应事件实际发生时带时区偏移的 ISO 8601 值。不得用当前时间伪造历史时间；可靠记录无法证明时写 `未知` 并说明原因。

该命名规范只约束新文档，不构成批量重命名既有文档的授权。存在多份相关文档时，逐份选择、确认、提交和判断完成状态，不把一份文档的授权或生命周期扩展到其他文档。

状态含义：

1. `编辑中`：仍在讨论，不能作为实施依据。
2. `已确认`：用户确认了当前内容，可以作为开发依据，但状态本身不授权执行。
3. `执行完毕`：全部内容已经实施，并通过相称的实际验证。

项目可以明确定义额外的规划、吸收、评估或发布状态。只有该项目的规则负责这些状态的含义、写入者和转换条件；全局 Skill 只在当前任务实际适用时遵循，不为其他项目创建同名文件或状态。

## 项目工作流交接

需求确认后不自动触发项目工作流或实施。只有用户明确提出执行意图时，才重新读取项目规则并选择执行器：

- 项目明确声明了适用于当前需求的执行工作流：把已确认需求和用户授权交给该工作流，不臆测其角色、文档类型或状态变化。
- 项目没有适用执行工作流，且需求处于`已确认`、自包含并符合通用执行边界：使用 `ftl-requirements-execution` 回退执行。项目使用额外生命周期时，还必须明确定义当前状态允许执行和完成后的状态转换。
- 需求直接创建、修改或替换项目 Harness 治理机制：目标 Harness 不能作为自己替代规则的唯一执行器，使用 `ftl-requirements-execution` 在其外部实施。
- 关键规则、执行能力或权限缺失：保持`已确认`并报告缺口，不猜测实施。

既有需求可能带有旧版全局 Skill 或项目规则定义的额外元数据。维护它们时按可靠来源保留和更新，不批量删除字段，也不把旧字段加入新建文档的默认模板。项目没有定义额外状态如何进入和完成执行时，保持原状态并报告缺口，不擅自映射到`已确认`或`执行完毕`。

## 保持当前需求自包含

修改执行完毕的历史基线时，新文档必须在本次范围内完整写清修改后希望生效的目标、业务规则、必要约束、需要保留的相关行为和验收预期。不得要求执行者递归拼接多份历史文档才能还原当前需求。

只记录直接相关的前序文档，以及确有助于避免误解的简短变更原因；不要复制无关模块或完整演变史。

## 确认

结合目标、范围、业务规则、关键选择、验收预期和可实施性，判断文档是否足以支持开发。

### 定稿前强制复核

提供 A/B 选项前，必须复核当前需求文档：

1. 是否仍有尚未与用户达成一致的目标、范围、业务规则或关键取舍；
2. 文档是否存在未完善、含义不明确或相互冲突的内容。

仍有关键缺口或用户提出修改时，保持 `编辑中` 并继续讨论。文档已经完善时，明确提供：

- `A：确认定稿`：确认并提交需求文档，不实施项目功能。
- `B：确认定稿并执行`：先确认并提交需求文档，再按“项目工作流交接”选择实际执行器，并以自包含的 `/goal` 持久目标实施。

只有用户明确选择 A 或 B，才把对应文档改为 `已确认` 并写入实际确认时间。含糊回答不能推定为确认或执行授权。

## 文档确认提交

确认后检查生命周期字段和实际内容，将本次确认的需求文档定义为独立的文档确认提交单元，使用 `ftl-local-commit` 创建本地 commit。只把该需求文档列为允许暂存的路径，不把其他文档或实现改动纳入本次提交。

无法创建提交时如实说明，不伪造提交，也不把文档确认提交失败解释为功能执行授权。

选择 A 后结束，不触发项目工作流、目标模式或项目功能。选择 B 后按下节完成目标模式交接。

## B 的目标模式交接

选择 B、完成需求确认提交并按项目规则解析实际执行器后，使用 `create_goal` 或等价的 `/goal` 能力创建持久目标，再由目标进入项目工作流或 `ftl-requirements-execution`。B 是明确的目标创建授权，但不能把 `B` 本身当作目标正文。

目标正文必须能够脱离隐含对话独立执行，至少写明：

- 已确认需求文档的精确路径和用户执行授权；
- 按当前项目规则解析出的项目工作流或全局回退执行器；
- 以整份文档的范围、验收预期、生命周期更新和没有剩余必需工作作为停止条件；
- 不扩大文档范围、外部副作用或 Git 权限。

目标模式只提供跨回合持续执行，不替代项目工作流判断、执行器职责、验证证据或本地提交。目标能力不可用、创建失败或已有目标冲突时，保持文档`已确认`，报告阻塞和继续条件；不得静默退回普通多轮实施，也不得因此改写文档完成状态。

## 用户回复的解释边界

“其他都可以”“按你的建议”等概括性同意，只覆盖助手在紧邻上一轮中明确列出的讨论项；不得把它扩展到助手随后新增的内容，也不得把它解释为确认整份需求文档、选择 A/B 或授权执行。
